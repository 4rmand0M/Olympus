INFORME TÉCNICO MAESTRO: INGENIERÍA DE SOFTWARE Y ESTABILIZACIÓN ERP v6.0

Proyecto: Estabilización Integral y Refactorización del Sistema ERP

Alcance: Resolución de Deuda Técnica, Seguridad, Rendimiento y Lógica de Negocio

Estado: Producción Estable

1. RESUMEN EJECUTIVO

El presente informe recopila la totalidad de las intervenciones estructurales y de mantenimiento realizadas sobre la base de código del proyecto desde su inicio. Durante las auditorías profundas del sistema, se identificaron y solucionaron decenas de fallas críticas que comprometían la compilación, el rendimiento, la seguridad de los datos y la experiencia del usuario. El sistema ha sido refactorizado extensamente para garantizar estabilidad a nivel empresarial.

2. REPOSITORIO Y COMPILACIÓN INICIAL (DEUDA TÉCNICA)

  • Conflictos de Exportación Duplicada: Existían declaraciones múltiples de export const y export default en módulos clave como ClientesModule.tsx y ProductosModule.tsx. Se fusionó la lógica y la interfaz en exportaciones únicas.
  • Sintaxis JSX Malformada: Se encontraron etiquetas sin cerrar y estructuras fragmentadas en ReportesModule.tsx y DashboardModule.tsx.
  • Dependencias Faltantes: Solución de errores relacionados con iconos importados de lucide-react que no correspondían a la versión instalada.
  • Exportaciones y Compilación Rota: Múltiples sentencias export default causaban fallos fatales en el bundler Vite impidiendo el despliegue.

3. FALLAS DE SEGURIDAD Y AUTENTICACIÓN (LOGIN)

  • Errores de Confirmación de Correo (Silent Login Failures): Al intentar iniciar sesión, los usuarios que no habían confirmado su correo electrónico a través de Supabase Auth generaban una excepción silenciosa. Esto dejaba el botón de login bloqueado en un estado de carga infinita sin feedback visual. Solución: Implementación de mapeo de errores específicos (ej. interceptar Email not confirmed) para redirigir al usuario o sugerir el reenvío del correo de confirmación.
  • Errores de Conexión con la Tabla de Usuarios (Fallo de Sincronización Auth-Pública): Se detectó un problema crítico post-login. Supabase validaba las credenciales correctamente, pero las políticas de seguridad (RLS) bloqueaban el cruce de datos con la tabla public.usuarios. El usuario iniciaba sesión con éxito, pero la pantalla se quedaba en blanco porque el sistema recibía un Error 403 (Forbidden) al intentar leer su rol o sucursal. Solución: Refactorización de las Row Level Security Policies para permitir a los usuarios autenticados leer exclusivamente su propio perfil usando auth.uid() = id.
  • Desincronización de Expiración de Tokens JWT: Cuando la sesión caducaba, la UI no se refrescaba, permitiendo al usuario llenar formularios que fallaban al guardar (401 Unauthorized). Solución: Interceptor de red que detecta errores 401 y redirige al login.
  • Políticas RLS Inseguras: Usuarios podían consultar facturas de sucursales a las que no pertenecían alterando el ID en las peticiones de red. Solución: Se aplicaron políticas estrictas en Supabase asociando la consulta al sucursal_id correspondiente.
  • Exposición de Claves Sensibles: Variables de entorno sin el prefijo VITE_ causaron problemas de empaquetado. Solución: Revisión estricta del .env.

4. ERRORES DE LECTURA E INTEGRIDAD DE DATOS (BASE DE DATOS)

  • Errores Severos al Leer Datos (Payload Too Large & Timeouts): El sistema intentaba descargar toda la tabla de movimientos e historial de facturas de un solo golpe al montar los componentes. A medida que la base de datos crecía, esto causaba cuellos de botella masivos, provocando Timeouts y errores de Payload en el navegador. Solución: Se migró todo el sistema de lectura a una arquitectura de Paginación Basada en Cursores (Cursor-based Pagination), leyendo los datos en bloques seguros de 50 registros.
  • Columnas Inexistentes en Consultas (PGRST204): El sistema fallaba al intentar renderizar vistas porque los hooks useCrud consultaban campos que no existían en las tablas: moneda, ciudad, unidad, tipo_doc, precio_venta, itbis_aplicado y observaciones.
  • Mapeo Explícito: Se refactorizaron todos los llamadas a useCrud para solicitar explícitamente los campos disponibles (ej. cambiar precio_venta a precio, y itbis a impuesto).
  • Saneamiento de Datos Basura: Se identificaron formatters locales que inyectaban caracteres extraños (ej. símbolos ¿) y monedas duplicadas en el renderizado de la UI. Se centralizó el formateo a través de Intl.NumberFormat.
  • Prevención de Bloqueos (Deadlocks) de Inventario: Los módulos intentaban renderizar nombres de productos haciendo búsquedas (find) sobre datos no cargados, lo que lanzaba excepciones. Se mitigó con Optional Chaining (?.).
  • Violaciones de Llaves Foráneas (Orphaned Data): Borrar un cliente con facturas asociadas causaba un error 500 debido a restricciones SQL. Solución: Alteración de tablas para incluir ON DELETE RESTRICT.
  • Integridad de Creación de Usuarios: Fallos en el trigger de la base de datos handle_new_user causaban que los metadatos de los nuevos registros no se sincronizaran con la tabla public.usuarios debido a valores nulos. Se robusteció con COALESCE.

5. ERRORES DE INTERFAZ Y MANEJO NUMÉRICO (UI/UX)

  • Desbordamiento de Datos Numéricos (Input Overflow): Un error crítico de UI/UX y lógica de datos. Al intentar insertar cantidades muy grandes (facturas por millones), el número literal se desbordaba físicamente fuera del contenedor del input. Además, al usar <input type="number">, valores inmensos provocaban truncamiento de precisión por los límites del MAX_SAFE_INTEGER en JavaScript. Solución: Se eliminaron los inputs numéricos nativos y se implementaron inputs de texto controlados con máscara de moneda que auto-formatean con comas (ej. 1,500,000.00). Para el envío al backend, se integró una librería de alta precisión (como Big.js) para evitar corrupción de datos.
  • Pérdida de Foco (Focus Loss) en Formularios: Los usuarios reportaban que al escribir un solo carácter en los inputs, el formulario perdía el foco. Se detectó que los componentes de formulario (FormFields) estaban declarados dentro del ciclo de renderizado principal, lo que causaba que React los destruyera y recreara en cada tecla. Se extrajeron al nivel superior del archivo.
  • Cálculos Financieros Peligrosos: El módulo de facturación utilizaba .toFixed(2) directamente sobre valores potencialmente nulos o no definidos (undefined). Se protegió la lógica forzando un fallback a numérico: (valor || 0).toFixed(2).
  • Condiciones de Carrera (Race Conditions) en Actualizaciones: Al guardar rápidamente varias facturas, el estado local se sobrescribía con datos antiguos. Solución: Sistema de concurrencia basado en marcas de tiempo.
  • Desincronización de UI Optimista (Optimistic UI Desync): Las interfaces asumían inserciones exitosas antes de la confirmación del servidor. Se implementó un rollback en bloques catch.
  • Excepciones Silenciadas (Swallowed Exceptions): Bloques try/catch vacíos ocultaban fallos en la red. Se implementó toast.error y logging centralizado.
  • Colisiones de Z-Index: Menús desplegables y modales quedaban ocultos detrás del Sidebar. Se estandarizaron las variables de z-index globales.
  • Desbordamiento de Viewport en Móviles: Tablas largas rompían el diseño en pantallas pequeñas, forzando un scroll horizontal en toda la página.
  • Advertencias de React "Uncontrolled to Controlled": Pasar undefined a inputs durante la carga de datos inicial disparaba errores en la consola. Inicialización segura de estado con cadenas vacías ''.
  • Desajuste de Hidratación (Hydration Mismatch): Fechas renderizadas causaban desincronización entre el servidor y el cliente debido a zonas horarias diferentes.

6. TIPADO ESTRICTO Y TYPESCRIPT

  • Incompatibilidad de ValueType en Recharts: Un error crítico en chart.tsx: Argument of type 'ValueType' is not assignable to parameter of type 'string | number'. La librería gráfica pasaba arrays en lugar de primitivos en gráficos apilados. Se agregó validación en tiempo de ejecución.
  • "Any-Hacking": Las definiciones de Supabase y las firmas de funciones abusaban del tipo any, suprimiendo las validaciones del compilador y posponiendo los errores al runtime. Se mejoró la inferencia de tipos en los flujos principales.

7. PROBLEMAS DE RENDIMIENTO (PERFORMANCE)

  • Fugas de Memoria en Suscripciones en Tiempo Real: Canales de Supabase abiertos sin instrucción de unsubscribe llenaban la memoria RAM congelando el navegador al cambiar de módulos. Solución: Funciones de limpieza en los hooks.
  • Problema de Consultas N+1 en el Dashboard: El sistema realizaba una consulta separada por cada ítem para obtener el nombre del producto, colapsando la base de datos. Solución: Uso intensivo de JOINs en las vistas SQL.
  • Ausencia de Debounce en Búsqueda: Los inputs disparaban consultas HTTP por cada tecla presionada causando bloqueos (HTTP 429 Too Many Requests). Solución: Retraso de red de 300ms implementado en un custom hook.
  • Bloqueos de Renderizado Síncrono: Tablas masivas se renderizaban de golpe bloqueando el Main Thread. Se implementó virtualización de listas.

8. MEJORAS DE NAVEGABILIDAD Y OPTIMIZACIONES GLOBALES

  • Atajo de Teclado Global: Implementación del atajo Ctrl + B para enfocar directamente la barra de búsqueda en ERPTopBar.tsx mejorando la eficiencia operativa.
  • Gestión Modular Segura: Reorganización del Sidebar con módulos inhabilitados visualmente para indicar futuras capacidades sin exponer rutas no terminadas al usuario final.

9. CONCLUSIÓN DEL MANTENIMIENTO

El sistema requirió una refactorización extensiva para cerrar brechas críticas de estabilidad, seguridad y rendimiento. Con estas múltiples correcciones aplicadas a nivel de infraestructura, autenticación (login) y presentación (overflow de inputs), el ERP opera ahora dentro de los estándares óptimos para entornos de alta transaccionalidad.
